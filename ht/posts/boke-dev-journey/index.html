从零到上线：小破站全栈博客开发全纪录

2026年6月15日 10 阅读 技术

缘起

2025 年春天，我决定从零搭建一个完全属于自己的二次元风格个人博客。市面上的博客方案太多——WordPress 太笨重，Hexo 太依赖主题，Notion 太封闭。我想要的是一个真正属于自己、每一行代码都亲手写的博客。

项目代号「小破站」，设计参考了 Mizuki 博客主题，但在视觉上做了差异化：樱花粉 (#E8738A) 与星夜蓝 (#6B7DB3) 的渐变配色、毛玻璃拟态卡片、全屏 Hero 轮播背景。

技术选型与架构

为什么选 Astro？

在 Next.js、Nuxt、Gatsby 之间犹豫了很久。最终选 Astro 的原因很简单：

  • 零 JS 默认：博客以内容为主，不需要 SPA 的运行时开销
  • SSR + Static 双模式：生产环境用 SSR 连接数据库，提交作业时打包成纯静态
  • MDX 原生支持：技术文章的代码示例、数学公式都能直接渲染

三端分离架构

用户 → Nginx(OpenResty) → /        → Astro SSR (:4321)
                          → /api/*   → Express API (:3000)
                          → /admin/* → React SPA 静态文件
                          → /uploads → 本地文件存储
                          ↓
                       MySQL 8.0 (Docker)

这不是传统的单体应用，而是三个独立服务通过 Nginx 反向代理统一入口。这样做的代价是部署复杂，但好处是每个服务可以独立开发、独立重启。

层级 技术选型 为什么
博客前端 Astro 6.x + Tailwind CSS 零JS、SSR/Static双模式
后台管理 React 19 + Ant Design 6 企业级组件库、中文生态
API 后端 Express.js + TypeScript 轻量、灵活、中间件丰富
ORM Prisma 6.x 类型安全、自动迁移
数据库 MySQL 8.0 Docker 1Panel 自带、稳定
进程管理 PM2 Node.js 进程守护
反向代理 OpenResty (Nginx) 1Panel 内置
服务器 雨云香港 2核2G 免备案、低延迟

第一阶段：项目初始化

搭建博客前端框架

用 create astro 初始化项目后，第一个任务是建立完整的页面结构。参考 Mizuki 主题的布局，我规划了 10 个页面：

  • 首页（index.astro）— 全屏 Hero + 功能卡片 + 统计数字 + CTA
  • 文章列表（posts.astro）— 分页卡片布局
  • 文章详情（posts/[slug].astro）— Markdown 渲染 + 评论
  • 归档（archive.astro）— 按时间线排列
  • 搜索（search.astro）— 全文检索
  • 关于（about.astro）— 个人介绍 + 技能栈
  • 友链（links.astro）— 友情链接展示
  • 图集（albums.astro）— 摄影作品网格
  • 追番（anime.astro）— 动画观看记录
  • 日记（diary.astro）— 时间线日记

配色方案使用 CSS 自定义变量，全局统一管理：

--color-primary: #E8738A;     /* 樱花粉 */
--color-secondary: #6B7DB3;   /* 星夜蓝 */
--color-accent-blue: #7EC8E3; /* 天空蓝 */
--color-bg: #faf8f6;          /* 暖白背景 */

UI 风格上采用了玻璃拟态（glassmorphism）——半透明背景 + 模糊 + 微边框，卡片悬浮时有轻微上浮动画。

遇到的第一个坑：全局 CSS 文件忘了导入，整个页面完全没有样式，白底黑字看了半小时。加一行 import ../styles/global.css 在 Layout 里就好了——但提醒了我 Astro 的样式隔离机制和传统前端不同。

搭建后台管理系统

管理后台用 Vite + React 19 + Ant Design 6 构建。初始版本只包含：

  • 登录/注册页面
  • 文章管理（CRUD 表格 + 表单）
  • 用户管理（列表 + 状态切换）
  • 站点设置（表单）
  • 仪表盘（统计卡片）

使用 React Router 7 管理路由，Axios 封装 API 客户端，JWT token 通过拦截器自动附加。

搭建 API 后端

Express.js + TypeScript 是经过深思熟虑的选择。Node.js 的好处是前后端统一语言，TypeScript 提供类型安全。Prisma 作为 ORM 比 Sequelize 和 TypeORM 都舒服——Schema 定义即文档，自动生成类型。

初始 API 路由：auth（认证）、posts（文章��、users（用户）、settings（设置）、stats（统计）

第二个坑：登录接口设计。第一版用 email + password 登录，但管理后台习惯用 username。修改方案是登录接口接受 account 字段，判断是否包含 @ 符号，有 @ 则按邮箱查，否则按用户名查。这个简单的 if-else 避免了前端两套登录表单的麻烦。

第二阶段：双模式架构

核心设计

博客需要同时支持两种运行模式：

  1. 生产模式 (SSR)：服务器渲染，连接真实 MySQL，用于线上
  2. 静态模式 (Static)：纯前端打包，使用内置 Mock 数据，用于作业提交和演示

这个需求催生了 lib/data.ts——整个博客的统一数据层：

const isStatic = import.meta.env.ASTRO_MODE === "static";
const API_BASE = isStatic ? "" : "http://127.0.0.1:3000/api/v1";

export async function getPosts(params) {
  if (isStatic) {
    const { mockPosts } = await import("./mock");
    return paginate(mockPosts);
  }
  return fetchAPI(`/posts?${qs}`);
}

每个数据获取函数都在顶部判断 isStatic，静态模式返回 mock 数据，SSR 模式 fetch API。这样在开发时写一套代码，打包时自动适配两种模式。

第三个坑：这个设计遇到了 Astro 最隐蔽的一个坑——import.meta.env 是编译时常量。

我做了非常愚蠢的一件事：在 .env 文件里写了 ASTRO_MODE=static，然后命令行执行 ASTRO_MODE=server npm run build。以为命令行参数会覆盖 .env……结果编译产物仍然用的是 mock 数据。

排查过程：

  1. 先怀疑 API 挂了 → curl 测试 API 正常返回数据
  2. 再怀疑 Nginx 配置 → 访问日志显示请求没打到 API
  3. 最后在 data.ts 里加了 console.log(isStatic) → 输出 true
  4. 搜索 Astro 文档才发现 import.meta.env 是 Vite 编译时替换的

解决：.env 文件里移除 ASTRO_MODE，只在构建命令中指定。

第三阶段：部署上线

Nginx 反向代理配置

三服务架构的 Nginx 配置是最折腾的部分。博客 SSR (:4321)、API (:3000)、后台静态文件必须统一从 80 端口访问，路径分别是 /、/api/*、/admin/*。

第四个坑：后台静态文件的路径配置。

第一个问题：alias vs root。后台 build 产物在 /opt/boke/apps/admin/dist/，我复制到了 /opt/1panel/www/admin/。用 alias 时 try_files 会导致路径拼接错误，报 403 Forbidden。改为 root /opt/1panel/www/ + try_files $uri $uri/ /admin/index.html 才解决。

第二个问题：OpenResty 容器无法访问宿主机文件。1Panel 的 Nginx 运行在 Docker 容器里，默认 mount 点只有 /opt/1panel/www/。所以只能把文件放在这个目录下。

第三个问题：CSS/JS 404。后台的 index.html 引用的是 /assets/xxx.js，但实际路径是 /admin/assets/xxx.js。在 astro.config.mjs 里设置 base: "/" 解决。

PM2 进程管理

原本用 nohup node 启动，但进程动不动就挂。换成 PM2 后好了很多：

pm2 start dist/index.js --name boke-api
pm2 start dist/server/entry.mjs --name boke-blog

第四阶段：前后端数据联通

这是整个项目最大的重构。之前博客前台用的是 Astro Content Collections——所有文章是本地 MDX 文件。后台发布到 MySQL 的文章在前台根本看不到。

需要把 6 个主要页面全部改为 API 驱动：index、posts、posts/[slug]、archive、search、anime。

工作量最大的是 data.ts 重写：

  • getPosts() — 带分页、分类筛选、标签筛选、搜索
  • getPostBySlug() — 按 slug 查文章详情（注意：这里有个坑）
  • getCategories() / getTags() — 分类和标签列表
  • getAnimeList() / getAlbums() / getLinks() — 各自的数据获取

第五个坑：getPostBySlug 返回的数据嵌套问题。

服务器的 GET /posts/:slug 返回格式是 { code: 0, data: { post: {...} } }，而 fetchAPI 函数做了 return json.data，所以上层拿到的是 { post: {...} } 而不是文章对象本身。于是 post.content 始终是 undefined，文章详情页一片空白。

修复方法：在 getPostBySlug 中多解一层：

const data = await fetchAPI(`/posts/${slug}`);
return data?.post || null;

第六个坑：后台编辑文章按 slug 查 vs 按 ID 查。

后台编辑页用 useParams() 拿到的是数字 ID（如 3），调用 api.get("/posts/3")。但服务器的 :slug 路由把 "3" 当作 slug 去查——当然找不到。新增了 GET /posts/admin/:id 路由，按数字 ID 查询，不限制 PUBLISHED 状态。

第五阶段：功能增强

文章编辑增强

用户提的需求很具体：文章编辑页加置顶开关和封面图字段。

看似简单，但遇到了经典的 Zod 校验问题。发布时表单数据里 excerpt、cover 等空字段被 Ant Design 传成了 null，而 Zod 的 .optional() 只认 undefined 不认 null——400 错误。

修复：所有可选字段加 .nullable()。顺便发现响应拦截器在遇到 400 时只显示 "Request failed with status code 400"，把服务端的真实错误消息丢了。

B站追番同步

这是整个项目技术含量最高的功能。目标是输入 B站 UID，自动拉取该用户的追番列表写入数据库。

遇到的问题清单：

  1. -352 风控校验失败：B站 API 直接拒绝无签名的请求。实现了 Wbi 签名算法——从 /x/web-interface/nav 获取 img_key 和 sub_key，通过固定混排表打乱后拼接，对请求参数排序并 MD5 签名。

  2. -400 请求错误：签名通过了但还是被拒。排查发现 ps=50 太大了——改成 ps=15 + 分页循环。

  3. rating 字段报错：以为 evaluate 是评分数字，结果发现是用户写的文字短评（如"故事讲述了青梅竹马之间…"）。用 isNaN() 判断后跳过。

  4. genre 是数组：styles 字段是 ["漫画改", "日常", "校园", "恋爱"] 数组，但数据库定义的是字符串。加 Array.isArray() 判断，数组则 join。

  5. progress 是空字符串：B站返回的 progress 有些是 "" 而不是数字。

  6. 字段名不匹配：总集数不叫 total 叫 total_count；评分不叫 evaluate 叫 rating.score（且是对象）；状态不叫 status 叫 follow_status（值 1/2/3 映射）。

最终方案：Cookie 认证 + 正确的字段映射 + ps=15 分页，终于稳定同步。

图集管理

需求：创建相册 + 上传图片 + 前台展示。涉及改动：

  • albums.ts 路由新增图片子路由 GET/POST/DELETE /:id/images
  • index.ts 新增 multer 文件上传 + /uploads/ 静态文件服务
  • AlbumsManage.tsx 新增图片管理弹窗（URL 添加 + 本地上传 + 删除）
  • albums/[id].astro 新建相册详情页（图片网格展示）

用户角色管理

给 UserList 加了一个「设为管理员/取消管理员」按钮，调用 PUT /users/:id 传 { role: "ADMIN" | "USER" }。实现了但发现这个接口没有任何权限检查——任何人登录后都能改角色。加了 requireAdmin 中间件才安全。

第六阶段：侧边栏与站点设置

侧边栏组件 API 化

四个侧边栏 Widget 全是硬编码的假数据：

  • StatsWidget："6 篇文章、3 个分类、10 个标签"——全是写死的
  • CategoriesWidget：三个假分类
  • TagsWidget：十个假标签
  • Announcement：一段日文假公告

数据层明明有 getStats()、getCategories()、getTags() 函数，而且 API 早就返回真实数据。问题是没有任何 Widget 调用它们。

改造方案：每个 Widget 在 Astro 的 frontmatter 中 await getXxx() 获取真实数据，然后用 Astro 模板语法渲染。关键是 Astro SSR 支持在 frontmatter 中写 await，数据在服务端获取后直出 HTML，不需要客户��� fetch。

同时：

  • 新增了标签/分类/公告的后台管理页面（参照 AlbumsManage 的 Table+Modal 模式）
  • 分类删除时先解除关联文章（updateMany categoryId = null）
  • 标签删除时利用 Prisma 的 onDelete: Cascade 自动清理 PostTag 关联
  • 文章编辑支持标签多选

站点设置持久化

这是踩坑最多的一个下午。

问题链：

  1. 后台设置页修改标题 → 提示保存成功 → 刷新又变回去了
  2. 查代码发现 settings.ts 用的是 let siteSettings = {...} 内存对象
  3. 改成了 Prisma 读写 site_settings 表 → 但 keywords 是数组，表单传的是逗号字符串
  4. 加了前后端格式转换 → 但忘了更新后台构建 → 还是旧代码
  5. 构建后台 → 服务器太卡、2核2G编译 TypeScript 超时
  6. 换 npx vite build 跳过 tsc → 构建成功 → 但博客崩了
  7. 查日志 → description is not defined → Layout 改造时变量声明丢了
  8. 修好 Layout → 博客 502 → MySQL Docker IP 漂移了

整个修复链条：设置持久化 → 字段格式转换 → 后台构建 → 博客构建 → Layout 变量 → MySQL IP → 最终全部稳定。

第七阶段：完善与收尾

评论区系统

虽然有 Comment 模型和 API 规范，但实际完全没实现。CommentSection 是一个纯静态占位符。

从零构建：

  • 服务端 comments.ts：GET 列表（含嵌套回复）、POST 发表（requireAuth）、PUT 审核、DELETE 删除
  • 前端 CommentSection.astro：SSR 预渲染评论列表 + 客户端 JS 提交表单
  • 后台 CommentManage.tsx：审核/驳回/删除

轮播图重构

Carousel 组件写好了但从未被任何页面引用。把它改成全屏 Hero 风格，替换掉旧的静态 Hero，成为首页第一屏。同步从设置页移除了 bannerImages 字段。

文章置顶

文章列表只按 createdAt 排序，置顶文章没优先。改 orderBy: [{ pinned: "desc" }, { createdAt: "desc" }] 一行解决。

技术总结

项目规模

  • 代码文件：约 120 个源文件
  • 数据库表：15 张（users, posts, categories, tags, post_tags, albums, images, anime_list, links, comments, docs, diaries, about, site_settings, announcements）
  • API 路由：15 个模块（auth, posts, users, settings, anime, albums, diary, links, about, stats, categories, tags, announcements, comments, health）
  • 后台页面：13 个管理模块
  • 前台页面：10 个公开页面
  • Git 提交：50+ 次

架构经验

  1. 双模式数据层的设计是对的。虽然多写了一些 if-else，但一次构建可以在两种环境下运行，对作业提交和演示非常友好。

  2. 三服务分离在运维上增加了复杂度。如果重来，可能会考虑把博客 SSR 和 API 合并成一个服务，后台静态文件继续单独部署。

  3. 每次部署都要重建博客。因为 Astro 是编译型框架，代码改了不 rebuild 就不会生效。服务器 2 核 2G 编译 TypeScript 慢是个实在问题。

  4. Git push 不稳定时，服务器直接改代码要格外小心。sed 和 python 脚本在服务器上很容易因为引号、换行符问题出错。

造轮子的意义不在于轮子本身，而在于你终于理解了它为什么是圆的。 —— 写于 2025 年 6 月，项目基本完成之际
